## Domain Reasoning

- Entities: Tank (position, orientation, health), Projectile (position, direction, owner), Obstacle (static blocking cells), Arena (bounded grid and obstacle layout)
- Rules: Movement is constrained by arena bounds and obstacles; orientation dictates move and fire direction
- Projectile lifecycle: spawn at tank muzzle, advance per tick, collide with tanks/obstacles/bounds, then despawn
- Damage model: tank takes damage on projectile hit; at 0 health tank is destroyed
- Win/score: track hits/kills; winner when opponent destroyed; game enters terminal state
- Tick loop: deterministic discrete ticks that apply queued commands then advance projectiles then resolve collisions
- Reset: restore initial state deterministically
- Separation: core logic pure and clockless; no real-time, IO, or randomness in domain modules

## Domain Expectations

- Movement and orientation: Tanks rotate or move forward based on orientation (N/E/S/W); moving into walls or obstacles is rejected
- Arena bounds: All positions must stay within [0..width-1] x [0..height-1]; projectiles leaving bounds are removed
- Obstacle blocking: Obstacles occupy fixed grid cells; tanks and projectiles cannot pass through
- Firing and projectile motion: Firing spawns a projectile in front of the tank if the spawn cell is free; projectile advances one cell per tick
- Collision and damage: Projectile hitting a tank reduces health; projectile is removed upon first collision
- Scoring and winner: When a tank’s health reaches zero, the opponent’s score increments; a winner state is set
- Deterministic tick order: Within a tick, apply tank commands (move/rotate/fire), then move projectiles, then resolve collisions, ensuring deterministic outcomes
- Reset and validation: Reset returns to initial positions, health, scores; invalid commands are ignored safely without side effects
