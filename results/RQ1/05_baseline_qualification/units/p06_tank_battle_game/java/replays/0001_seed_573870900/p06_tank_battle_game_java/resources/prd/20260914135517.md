## Domain Reasoning

- Entities and immutability: Position is an immutable value object with translate producing a new Position; Orientation is an enum with dx/dy and left/right; Command enum defines MOVE_FORWARD, TURN_LEFT, TURN_RIGHT, FIRE.
- Tank lifecycle and state: Tank has mutable position, orientation, and health; id must be nonblank; health can be zero (dead) but not negative; isAlive checks health>0; copy must support dead tanks; rotation and movement mutate state.
- Projectile semantics: Projectile holds shooterId, mutable Position via setPosition and immutable Orientation; GameEngine may only move projectiles via setPosition; copy provides defensive copies.
- Arena and obstacles: Arena validates positive width/height; bounds checking ensures positions within [0,width-1] x [0,height-1]; obstacles are stored in ObstacleMap as a set of immutable Position values; Arena defensively copies obstacles; inBounds and isObstacle queries.
- GameEngine ownership and copies: initialArena and initialTanks are deep snapshots; current arena is mutable via reset assignment this.arena = initialArena.copy(); current tanks map is the only live state; constructor makes two independent Tank copies per supplied tank using the literal statements in order; never mutate or reuse initialTanks as current state.
- Tick processing and ordering: For each live tank, at most one queued command is processed per tick in lexicographic tank-id order; MOVE_FORWARD attempts one step considering bounds/obstacles/other live tanks; TURN_LEFT/RIGHT mutate orientation; FIRE spawns a projectile in the forward cell only if in bounds and not obstacle.
- Projectile update and collisions: In same tick, each projectile advances exactly one cell using setPosition; remove projectile if out of bounds, hits obstacle, or hits the first non-owner live tank at that cell; applyDamage(1) to the hit tank; record addHit(shooterId) always; addKill(shooterId) only if health drops to zero; projectile consumed upon hit.
- ScoreBoard ownership: ScoreBoard holds hit and kill maps initialized for initial tank ids; GameEngine must invoke scoreBoard.reset(initialTanks.keySet()) during reset, never access private fields, and never replace scoreBoard; getScore returns hits + 5*kills; provide fresh defensive copies.
- Reset semantics: reset assigns this.arena = initialArena.copy(); assigns this.tanks = new HashMap<>(); iterates initialTanks.values() without streams to copy each into current tanks; recreates empty command queues; clears projectiles; calls scoreBoard.reset(initialTanks.keySet()).
- Winner determination: winner returns the sole surviving tank id only when exactly one of the at-least-two initial tanks is alive; otherwise null.

## Domain Expectations

- Position: immutable with getX(), getY(), translate(int dx,int dy), equals/hashCode value semantics
- Orientation enum: NORTH(0,-1), EAST(1,0), SOUTH(0,1), WEST(-1,0) with dx(), dy(), left(), right()
- Command enum: exactly MOVE_FORWARD, TURN_LEFT, TURN_RIGHT, FIRE
- Tank: mutable position/orientation/health; nonblank id; health>=0; copy supports dead tanks; applyDamage reduces health floor at zero
- Projectile: mutable position via setPosition only; GameEngine never calls undeclared mutators; copy returns a defensive snapshot
- ObstacleMap: empty factory; add(Position); isBlocked(Position); copy returns a deep copy of positions
- Arena: validates positive dimensions; defensive copy of obstacles; inBounds(Position) and isObstacle(Position); copy returns a deep copy
- GameEngine: no streams; processes commands per live tank lexicographically; spawns and advances projectiles; records hits/kills; provides reset and winner; exposes defensive copies for tanks/projectiles/scoreboard

## Product Goals

- Deliver a deterministic, testable core for a tank battle game with clear, stable APIs
- Enforce strict separation of immutable/mutable state and snapshot/reset semantics
- Keep the project easy to maintain: small files, explicit ownership, no hidden side effects

## User Stories

- As a developer, I can enqueue commands for tanks and run deterministic ticks to observe movement and rotation.
- As a developer, I can fire projectiles and see correct hit/kill resolution and scoring updates.
- As a developer, I can reset the game to its initial snapshot, restoring tank states, arena, and clearing projectiles and scores.
- As a developer, I can query the current arena bounds and obstacles to ensure movement decisions are validated.
- As a developer, I can determine the winner when only one tank remains alive.
