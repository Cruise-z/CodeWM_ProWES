## Domain Reasoning

- ReleaseState lifecycle defines valid transitions: DRAFT -> REVIEW -> PUBLISHED, with enforcement of invalid transition errors
- Template placeholder substitution is deterministic: literal {{key}} replaced only when key exists; missing keys remain
- Validator ensures headline/body non-null non-blank; contact must include exactly one @ and non-empty local/domain parts
- PressRelease aggregates identity, content, template, custom fields, tags, state, and version history; starts DRAFT
- Publish operation in REVIEW appends exactly one Version number 1 with rendered plain text; no timestamps or randomness
- TaggingSystem supports searching releases by exact trimmed tag, preserving input order
- RenderService delegates plain-text output to release.renderPlainText to keep services stateless and decoupled
- Collections exposed are defensive copies preserving insertion order to ensure deterministic tests

## Domain Expectations

- ReleaseState is exclusively defined in src/main/java/ReleaseState.java with constants DRAFT, REVIEW, PUBLISHED
- Version is exclusively defined in src/main/java/Version.java with fields number and renderedText, getters, and value-based equality
- Template.applyCustomFields(Map<String,String>) replaces {{headline}}, {{body}}, {{contact}}, and any provided custom keys; null map treated as empty
- Validator.validateHeadline, validateBody return true only for non-null non-blank; validateContact requires single @ with non-empty sides
- PressRelease.validate returns true only if headline, body, contact are all valid according to Validator
- PressRelease.submitForReview requires state DRAFT and validate()==true; otherwise throws IllegalStateException
- PressRelease.publish requires state REVIEW; adds one Version(1, renderPlainText()) on first publication and moves to PUBLISHED
- TaggingSystem.searchByTag returns releases whose tags contain the exact trimmed tag, preserving the input list order

## User Stories

- As a PR manager, I can define a press release using a template with custom fields and placeholders
- As an editor, I can validate a release, submit it for review, and then publish it if valid
- As a marketer, I can tag releases and search for them by tags
- As a reviewer, I can render the release to plain text deterministically during review
- As an auditor, I can view version history with a deterministic rendered snapshot upon publication
