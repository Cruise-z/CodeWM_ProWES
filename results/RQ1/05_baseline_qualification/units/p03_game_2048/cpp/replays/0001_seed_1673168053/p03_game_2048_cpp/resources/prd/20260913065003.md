## Language Convention Requirements

- Use CMake with targets for library and executable; tests run via ctest.
- Use include/*.h and src/*.cpp pairs for reusable modules; tests include headers only.
- Every header must be self-contained and list all necessary standard-library includes.
- Every source must include the standard headers it directly uses; do not rely on transitive includes.
- Project-specific rule: any header that declares a size or index type must include <cstddef> directly and use std::size_t; bare size_t is forbidden. Do not use an integer shift whose width equals or exceeds the left operand's width.

## Domain Reasoning

- Core domain is a 4x4 grid of tiles with integer values.
- Moves (up, down, left, right) compress tiles, merge equal adjacent tiles once per move, and accumulate score.
- Tile spawning after valid moves must be deterministic for tests (no real RNG in core logic).
- Game states include: ongoing, win (tile 2048 reached), loss (no valid moves), and reset.
- Boundary concerns (UI, I/O, clock, randomness) must be separated from core logic for determinism and testability.
- Validation of inputs: only valid move directions; reject invalid commands without side effects.

## Domain Expectations

- 4x4 board stored in a deterministic, indexable structure (row-major).
- Directional moves apply slide-then-merge-then-slide with single-merge-per-line rule.
- Score increases by the value of produced merged tiles during a move.
- Deterministic tile spawn after a successful move: fixed policy (e.g., first empty cell in row-major, value 2) to guarantee reproducible results.
- Win condition triggers when any tile reaches 2048 exactly after a move.
- Loss condition triggers when no legal moves remain and the board is full.
- Reset returns the board to initial deterministic state with two tiles placed deterministically.
- Public API exposes immutable views of board, score, and state; mutating operations validate preconditions and report results.

## Product Goals

- Deliver correct and deterministic 2048 core mechanics in C++17.
- Keep architecture clean: domain logic isolated from runtime and test harness.
- Provide a minimal, robust automated test path using ctest.

## User Stories

- As a player, I can start a new game with a deterministic initial board.
- As a player, I can perform moves (left, right, up, down) and see tiles merge and score update.
- As a player, I can reach a win state when creating a 2048 tile.
- As a player, I can detect a loss state when no moves remain.
- As a player, I can reset the game to a known initial state.

## Requirement Analysis

We need a C++17 project with clean include/src separation, deterministic core logic, and exactly one concise test file. The architecture must provide a domain module modeling the 4x4 grid, move/merge rules (single merge per tile per move), score updates, deterministic tile spawning, and game state transitions (ongoing/win/loss/reset). Randomness and I/O are boundaries; tests must not rely on real RNG or user input. The build and test protocol is fixed: CMakeLists.txt, src/Main.cpp runtime entry, tests/test_main.cpp single test target, executed via ctest. Headers must be self-contained and obey the std::size_t and <cstddef> inclusion rule. Runtime entry should provide a small non-interactive demo and exit safely.
