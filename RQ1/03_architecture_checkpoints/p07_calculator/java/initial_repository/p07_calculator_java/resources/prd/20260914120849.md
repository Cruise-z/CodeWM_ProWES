## Domain Reasoning

- Expressions must be tokenized into numbers, operators (+, -, *, /), and parentheses while ignoring whitespace
- Parser/evaluator must respect operator precedence and parentheses; support unary minus for negative numbers
- Floating-point decimal values are accepted; precision management and division behavior must be deterministic
- Error handling must detect invalid tokens, malformed expressions, mismatched parentheses, and division by zero
- History should record successful calculations (expression, result) and optionally failed attempts (expression, error) without using system time
- Core domain must be pure and testable; runtime demo should only orchestrate IO-free usage

## Domain Expectations

- Tokenization: digits and decimal point form numbers; whitespace is skipped; operators and parentheses are separate tokens
- Unary minus handling: a '-' at start or after '(' or another operator binds as unary to the following number or parenthesized expression
- Operator precedence: '*' and '/' have higher precedence than '+' and '-'; parentheses override precedence
- Associativity: all binary operators are left-associative
- Division by zero results in a domain error with a clear message; no Infinity/NaN in user-facing result
- Input validation: invalid characters or malformed decimal formats (e.g., multiple dots) raise a tokenization error
- Mismatched parentheses or incomplete expressions raise a parse error
- History service: holds recent calculations in memory with bounded capacity (e.g., last 100 entries), retrievable in insertion order

## Product Goals

## Requirement Analysis

We must ship a Maven-based Java 11 project that exposes a small, canonical API to evaluate arithmetic expressions with +, -, *, /, decimals, unary minus, and parentheses. The architecture separates pure domain logic (tokenizer, parser/evaluator, error model, history) from runtime entry (a thin demonstration) and from tests. Errors must be explicit and human-readable; division by zero and malformed input are handled. One JUnit 5 test file validates wiring and representative rules. Main.java runs a short, non-interactive demo. All source files remain in the default package with no GUI and no external runtime dependencies. pom.xml pinpoints JUnit Jupiter and a Surefire version that runs JUnit 5, satisfying the protocol contract. Files are kept under ~150 LOC each, ordered by dependency for incremental implementation.
