## Domain Reasoning

- Workbook with sheets requires in-memory structures for cells, rows, and columns with type-safe access and missing value representation.
- CSV import/export must be robust to quoted fields, separators, line endings, and missing/invalid values, mapping to domain types deterministically.
- Column selection and filtering should operate over typed columns with predicates and composable conditions.
- Sorting with stable and deterministic rules, handling missing values with explicit ordering policy.
- Aggregation functions (sum, count, average) must ignore invalid values, handle missing values, and define behavior for empty sets.
- Deterministic processing reports summarize operations performed, counts of rows kept/dropped, invalid values encountered, and timing-free metrics.
- Separation of domain logic from runtime/IO ensures testability and determinism; CSV file system boundaries are abstracted via streams.

## Domain Expectations

- Workbook and Sheet entities support appending rows and accessing cells by column index or name.
- Cells represent values as strings internally with typed parsing (int/double/string) and missing value signals.
- CSV import reads from std::istream into a Sheet, supporting configurable delimiter and header presence.
- CSV export writes a Sheet to std::ostream with consistent quoting and missing value representation.
- Filtering API supports predicate-based row filtering with logical conditions on columns.
- Sorting API supports ascending/descending order on one or multiple columns, with explicit missing value order policy.
- Aggregation API supports sum, count, average over numeric columns with missing/invalid skipping.
- ProcessingReport provides deterministic counts (rows read, kept, dropped, invalid cells) and descriptions of applied operations.

## Product Goals

- Deliver a clear, canonical C++17 API for tabular processing with CSV interchange.
- Ensure deterministic, validated processing with robust missing/invalid handling.
- Keep architecture minimal (6–8 files) with clean separation of domain and runtime, and a concise automated test path.

## User Stories

- As a data analyst, I can import a CSV with headers into a sheet and inspect columns.
- As a user, I can filter rows where a numeric column exceeds a threshold and then sort by a secondary column.
- As a user, I can aggregate numeric columns to compute sum and average while ignoring invalid entries.
- As a user, I can export the processed sheet to CSV with proper quoting and missing values preserved.
- As a user, I receive a deterministic processing report summarizing rows read, filtered out, invalid cells, and operations performed.

## Requirement Analysis

We must build a medium-size C++17 project that cleanly separates domain logic from runtime and uses only the standard library. The protocol requires CMakeLists.txt, src/Main.cpp, and tests/test_main.cpp. The architecture should provide workbook-like structures; robust CSV import/export; column selection/filtering; sorting; aggregation; missing/invalid value handling; and deterministic processing reports. Tests must be concise and deterministic, including runtime wiring and a representative rule.

Planned repository files (6–8 total, exactly listed and consistent):
1) CMakeLists.txt (build configuration, C++17, one library target, one test target, enable ctest)
2) src/Main.cpp (runtime entry: small, non-interactive demo wiring the API, reading from string streams, printing a brief result)
3) tests/test_main.cpp (single protocol-level test: includes headers only; covers CSV import, filter+sort+aggregate behavior with missing values, and report determinism)
4) include/ExcelCore.h (public API: Workbook, Sheet, Row, Cell types; CSV import/export helpers; header-only declarations with necessary std includes)
5) src/ExcelCore.cpp (implement sheet storage, cell parsing, CSV read/write with robust quoting, missing handling)
6) include/ExcelOps.h (public API: column selection, predicates, filtering, sorting, aggregation, ProcessingReport)
7) src/ExcelOps.cpp (implement filtering, stable sorting with missing ordering policy, aggregations with invalid skipping, report generation)

Canonical public API: ExcelCore::Workbook/Sheet for data model and CSV I/O; ExcelOps functions for processing (selectColumns, filterRows, sortRows, aggregateColumn, buildReport). Runtime and tests use only these headers.

Design implications: headers are self-contained; sources include algorithm headers; CSV parsing is streaming-based; missing values represented as empty strings or explicit markers; invalid numeric parsing tracked in report; sorting defines deterministic tie-breakers. No network or OS-specific code.
