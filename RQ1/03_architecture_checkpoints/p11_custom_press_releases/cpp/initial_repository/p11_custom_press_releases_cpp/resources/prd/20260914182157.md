## Domain Reasoning

- Core entities: PressRelease, Template, VersionEntry, and AudienceTag; manage fields such as headline, body, contact.
- Lifecycle state machine: Draft -> InReview -> Published with validation gates.
- Template engine: placeholder substitution with a stable grammar, resolving required and optional fields; detect missing keys.
- Validation: enforce non-empty headline/body/contact; basic contact format checks; ensure tags are managed and searchable.
- Search/index: support filtering by audience tags and text search of headline/body; keep domain pure and storage in-memory for demo.
- Rendering: plain-text rendering independent from IO; deterministic rendering output.
- Version history: append-only immutable VersionEntry with timestamp supplied by a clock boundary (injected for determinism).
- Boundaries separated: no filesystem/network; runtime demonstrates composition; tests exercise only domain API.

## Domain Expectations

- PressRelease maintains a lifecycle with allowed transitions only (no publishing invalid drafts).
- Template placeholders like {{headline}} and {{contact.email}} substitute from provided custom fields.
- Validation rejects missing headline, body, or improperly formatted contact email/phone.
- Audience tags can be added, removed, and used to filter/search releases.
- Plain-text rendering outputs template with substituted fields and appropriate line breaks.
- Version history records each content mutation with a provided clock value and description.
- Search supports case-insensitive contains match over headline/body and tag inclusion.
- Canonical API exposes pure functions and small classes to compose in runtime.

## Requirement Analysis

We must build a medium-size C++17 repository that cleanly separates domain logic (templating, lifecycle, validation, tags/search, rendering, versioning) from runtime. The interface protocol demands exactly CMakeLists.txt, src/Main.cpp, and tests/test_main.cpp, with tests using only headers. The domain core will be header/implementation pairs under include/ and src/. We'll define a canonical public API surface via a small set of headers (e.g., PressRelease.h, TemplateEngine.h, Validator.h, Renderer.h, SearchIndex.h, VersionHistory.h, Clock.h) that expose pure logic and avoid I/O. The runtime entry composes these to produce a short deterministic demonstration that exits. Tests will cover wiring and a representative rule (e.g., invalid publish blocked, and placeholder substitution correctness). To avoid circular dependencies, modules will depend directionally: foundational value types and utilities first (e.g., Clock, StringUtil), then template/validator, then entity PressRelease which uses validator and versioning, then renderer and search indexing which depend on core entities. Public API must be exhaustive, with precise signatures and error behaviors documented and consistent across headers and tests.
